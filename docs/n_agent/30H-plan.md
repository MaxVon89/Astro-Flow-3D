## Plan: Persistent GPU run for ~30 hours

TL;DR
Run the pipeline/training persistently on available GPUs for the next ~30 hours using a supervised, containerized runner orchestrated by systemd (or a supervisor) with robust checkpointing, autos-restart, monitoring, and provenance capture. Validate with smoke tests and automated validators; resume from checkpoints on failure.

**Steps**
1. Environment readiness (parallelizable)
   - Confirm drivers, CUDA and cuDNN versions and that GPUs are visible (`nvidia-smi`).
   - Choose runtime: containerized (`docker`/`nvidia-docker2`) or native venv. Document chosen path in `runbook`.
   - Ensure Python deps installed (from `requirements.txt`) and that training code runs in the chosen runtime.

2. Pick run configuration (depends on Step 1)
   - Create a concise experiment config (yaml/json) with: dataset path, checkpoint dir, batch size, lr, number of epochs/steps, device assignment, checkpoint frequency (minutes/steps), and logging targets.
   - Store configs under `configs/experiments/` so runs are reproducible and referenceable.

3. Checkpointing & resume policy (critical)
   - Ensure training saves checkpoints atomically and frequently (e.g., every 10–30 minutes or N steps).
   - Add lightweight resume logic: on start, detect latest checkpoint and resume instead of starting fresh.
   - Persist checkpoints to a stable path, e.g., `artifacts/experiments/<run-id>/checkpoints`.

4. Logging, artifacts and provenance (parallel with 3)
   - Record stdout/stderr to rotating logs in `artifacts/experiments/<run-id>/logs`.
   - Save metadata: git sha, `configs/experiments/<name>.yaml`, environment (`pip freeze`), and CUDA driver versions to `artifacts/experiments/<run-id>/manifest.json`.
   - Ensure training emits machine-readable metrics (JSON lines) for validation and monitoring.

5. Supervisor/daemon orchestration (depends on Step 1–4)
   - Choose a runner: `systemd` service or `supervisord` to run the experiment process persistently and restart on failure.
   - Configure service to: use GPU devices (via container runtime or environment variables), run as non-root user, restart on failure with backoff, and write journaled logs to disk.
   - Include an explicit pre-start smoke test that verifies access to GPUs and that the training entrypoint is executable.

6. Resource reservation and contention policy (parallel with 5)
   - If multiple jobs or users share the node, use `CUDA_VISIBLE_DEVICES` to pin GPUs or use a simple local reservation file that the launcher checks and sets atomically.
   - For multi-GPU training, ensure NCCL environment variables and network configs are set; for single-GPU runs keep config simple.

7. Monitoring & alerts (parallel with 5)
   - Tail logs and monitor GPU health with `nvidia-smi` at intervals; emit health metrics (GPU utilization, memory usage, process status) to logs.
   - Optional: integrate with a monitoring stack (Prometheus + Grafana) or simple email/Slack alerting on failures or low GPU utilization.

8. Validation and automated checks (continuous)
   - Add validators that run after each checkpoint: file integrity, minimal reconstruction/forward pass on a fixed validation shard, and basic science metrics (reconstruction RMSE, sanity band-ratios).
   - If a validator fails, mark the run and notify via logs/alert; do not auto-delete checkpoints.

9. Controlled shutdown and handoff (end of ~30 hours)
   - Plan an automatic graceful stop at the 30th hour: send SIGTERM, let training finish a final checkpoint, then archive artifacts (tar or copy to long-term storage) and mark run as completed in manifest.
   - If continuous operation is desired after review, add a manual approval gate before continuing.

10. Smoke tests and dry-run before the ~30‑hour window
   - Perform a dry-run (single-step / single-batch) under the supervisor with checkpoint and resume enabled.
   - Verify that: benchmarks start, checkpoints are written, resume works, logs populate, and validators pass on the tiny shard.

**Relevant files to create or update**
- `configs/experiments/<name>.yaml` — experiment config template and run instances.
- `artifacts/experiments/<run-id>/manifest.json` — autogenerated run provenance and metadata.
- `s_agent/agent.py` or `experiments/run.py` — ensure runner supports resume and checkpoint config (the agent should call these; do not modify training internals during runtime without approval).
- `configs/preprocessing.yaml` — ensure normalization mode and parameters are explicit for reproducibility.
- System service: `/etc/systemd/system/astroflow-experiment-<run-id>.service` — supervisor unit (document only).

**Verification**
1. Pre-flight: `nvidia-smi` shows expected GPUs; a 1–2 step dry-run completes and writes checkpoint and logs.
2. Mid-run: every checkpoint is present and validators pass on latest checkpoint; GPU utilization > 20% (configurable threshold) for a majority of runtime.
3. Post-run: final manifest contains git sha, config, environment snapshot, and a list of artifact files; a short artifact sanity-check (e.g., confirm checkpoint loads and a forward pass runs) passes.

**Decisions & Assumptions**
- Assumes Linux hosts with proper NVIDIA drivers and Docker or Python environment available.
- Assumes moderate privilege to install/enable a systemd unit and write to `/etc` if systemd chosen; otherwise use user-level supervisor or tmux with a watchdog script.
- This plan favors reliability and reproducibility over maximal performance tuning (tuning can follow once the persistent runner is stable).

**Further considerations**
1. If you have cluster resource management (SLURM/Kubernetes), prefer submitting a scheduled job with preemption handling instead of systemd. Option: add a SLURM job script template and use `sbatch` for allocation.
2. For multi‑GPU multi‑node training, add a distributed launcher and checkpoint sharding strategy and test on a small scale before full run.
3. For long-term storage or team access, archive artifacts to an NFS/SMB mount or object storage (MinIO/S3) after run completion.


Runbook note for the coding agent consuming this plan: implement the experiment runner, a systemd supervisor description, checkpoint + resume logic, logging/manifest writing, and the smoke-test harness in that order. Prioritize checkpointing/ resume and smoke tests before autonomously enabling the ~30‑hour persistent run.
